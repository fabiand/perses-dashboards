# UX Design Principles

## Recording Rules Design

### Core Philosophy
**Start with the use-case.** Design recording rules around specific operational use-cases, not because you can measure something.

### Principles

**1. Focus on the Domain**
Organize rules around the resource you're measuring - memory, CPU, I/O. Don't force everything into generic patterns. Memory has different use-cases than CPU, so the metrics should reflect that.

**2. Capture Multiple Use-Cases**
Each resource has several use-cases you need to cover:
- Memory: utilization (are we running out?), overcommit (are VMs getting greedy?), swap (are we spilling to disk?), OOM risk (is something about to die?)
- CPU: allocation (who's using what?), overcommit (how many virtual CPUs vs real ones?), contention (are things waiting?)
- I/O: device busy time (how saturated?), latency distribution (how fast?), imbalance (why is one node slower?)

**3. Dimensional Consistency**
Stick to the same label names when they mean the same thing:
- **tier**: what kind of hardware (DRAM, swap)
- **scope**: who gets to use it (system, workloads)
- **utilized**: is it in use (true = used, false = free)
- **temperature**: how recently touched (hot = working set, warm = inactive cache)

**4. Pre-Calculate Ratios**
Do the math in recording rules, not dashboards. Utilization, overcommit, imbalance - calculate them once, use them everywhere. Dashboard queries should just fetch the answer.

**5. Naming Convention**
Follow Prometheus colon hierarchy: `namespace:level:metric:unit{labels}`
- `openshift:node:memory:bytes` - per-node memory
- `openshift:cluster:cpu:utilization:ratio` - cluster CPU utilization
- `openshift:vm:memory:overcommit:ratio` - per-VM memory overcommit

## Dashboard Design

### Core Philosophy
**You should know if there's a problem in 5 seconds.** No mental math, no memorizing what "good" looks like, no digging through docs.

### Principles

**1. Color-Driven Assessment**
Green, yellow, or red tells you what to do. Thresholds encode the operational knowledge so you react to color, not numbers. Green = chill, yellow = keep an eye on it, red = go fix it.

**2. Spatial Consistency**
Put the same thing in the same spot every time. Utilization is always first, Pressure second, Imbalance third, resource-specific fourth. Switch from Memory to CPU to I/O - same layout, different data. Your eyes know where to look.

**3. Resource-Agnostic Titles**
Call it "Utilization" everywhere, not "CPU Utilization" on one dashboard and "Memory Utilization" on another. The panel group title ("At a Glance - CPU") gives you the context. Less clutter, more consistency.

**4. Self-Documenting Panels**
Every panel description ends with "Answers: <question>?" so you know what it's for. No hunting through docs to figure out what a metric means.

**5. Progressive Disclosure**
Start high-level, drill down as needed. Overview shows 12 key metrics. Click one, you get the full resource dashboard. Click deeper, you get per-node breakdowns and history. Don't dump everything on screen at once.

### Anti-Patterns

**Don't do this:**
- Raw metrics without color thresholds - makes people do math in their heads
- Different gauge ordering on different dashboards - breaks muscle memory
- Resource name in every gauge title ("CPU Utilization", "Memory Utilization") - clutters the UI
- Panel descriptions that don't explain what the panel is for
- Everything-on-one-screen dashboards - overwhelming and nobody can find anything

### What Good Looks Like

If it's working, operators can:
1. Scan the Overview and know if something's broken (5 seconds or less)
2. Click the red thing and land on the right dashboard (10 seconds total)
3. Understand what the metric means without leaving the dashboard
4. Switch between dashboards without getting disoriented
